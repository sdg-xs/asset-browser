# Curated asset library design

## Intent and approved scope

Build a staff-only, local-first catalog of reusable asset definitions above the existing IFC source indexes. The user approved the design decisions Q1–Q13 and explicitly requested writing-plans followed by subagent-driven-development and frontend-design. A library entry is a specific product or a generic specification variant. Main browsing contains approved definitions, across sources, rather than source-model GUID cards. Existing facility management, import connectors, digital-twin placement, RFA, Nucleus and original IFC editing remain deferred.

## Domain and identity

An entry has an independent UUID, name, description, kind `generic` or `product`, optional family label, one canonical category, search tags, curated manufacturer/model values, specifications, and lifecycle `draft`, `approved` or `archived`. A product requires staff-confirmed manufacturer and model. Generic drafts permit missing identity and specifications; publication requires a nonblank name/category and at least one known reusable specification, or confirmed product identity. Explain incomplete records in the review workspace. All approvals are explicit, including batch approval. Archiving an entry is independent of hiding an IFC source.

Canonical categories are seeded from effective `Identity Data / Generic Hard Asset` values. Import preserves original labels and does not automatically alias plural or related meanings. Staff can rename canonical categories and map aliases to them. Each category has a template containing field mappings, display labels, data kinds, canonical units and roles `specification` or `variant`. Common identity fields appear on every entry. IFC-derived template fields begin as suggestions and require confirmation. Keep source values and staff overrides separate; missing is distinct from zero, false and conflict.

An IFC source record identifies model ID, source fingerprint, type GlobalId, source name/class, occurrence IDs, original categories and reusable property observations. Entries refer to one or more source records and occurrence subsets. GUIDs and Express IDs locate source data; they do not identify library cards. All occurrence values, including instance-derived specifications, are considered. Type values are fallback per property only when the instance property is absent. Technical IFC identity, asset IDs, room, level, offsets, placement and installation labels are source details, not suggested reusable specifications. Source inspection still exposes raw IFC properties.

## Normalization, comparison and variants

Read property measure types and source units. Normalize recognized SI/conversion-based length, area, volume, power, flow and voltage values to m, m², m³, W, m³/s and V respectively. Preserve the original display value/unit. If a unit or property is unsupported, retain it as text/unknown rather than pretending the value was normalized. Compare finite numeric values at a small deterministic tolerance, never parse missing markers as zero. Treat `n/a`, `NA`, blanks and exporter manufacturer `Revit` as absent product identity. Name-derived product hints are suggestions only.

For each mapped field, distinguish consistent, missing and conflicting values across occurrences. The entry's source suggestion uses the consistent value; conflicting values require staff resolution. Choosing an override preserves the underlying conflict record and marks it resolved for publication. Confirmed variant fields define which specification differences can create separate cards. Staff can split a draft by selected variant fields, preserving occurrence partitions and source links. Each resulting variant starts as a draft. Same-name types and unknown specifications never trigger automatic merging.

Suggest duplicate candidates using equal normalized category plus either confirmed product identity or equal nonempty comparable specification sets; equal readable names can produce lower-confidence review suggestions. Differences and missing comparison evidence are visible. Staff selects a target and confirms a merge, which combines source references without overwriting curated target fields. The result returns to draft for review, and absorbed entries are archived. This explicitly prevents blind name deduplication.

## Source refresh and persistence

Persist catalog definitions, categories, templates, source observations and overrides separately in `.local-data/catalog-library.json`, schema version 1. Keep the existing `.local-data/library.json` unchanged in structure. Atomic serialized writes and a monotonically increasing catalog revision prevent stale tabs from overwriting decisions. Mutations carry the expected revision; conflicts return structured HTTP 409 and refresh the UI without silently replaying staff decisions. Validate all requests with Zod and reuse localhost restrictions.

Importing the same model/type/fingerprint is idempotent. A changed source updates its observation record, preserves approved definitions and overrides, and flags review where values changed. New types become drafts. Missing or hidden sources leave approved definitions intact and mark geometry availability. Source references are checked against the visible current inventory before preview. Use the preferred source/occurrence first and then only confirmed equivalent references. Preserve existing download revision binding and viewer failure recovery. A source change during preview must never resolve a newly different type as an approved entry without review.

IFC source indexing remains browser-based. A worker analysis request returns reusable observations for all classified occurrences, compacted by distinct field/value and occurrence membership; it does not extract building geometry or send every raw property panel to persistent storage. Reuse property-set caches and report progress. Geometry and full raw properties load only on inspection. Existing BS19/JV3 indexes can be used to open and analyze their sources without deleting local data. Import drafts through an explicit staff action; do not approve fabricated demonstration assets.

## UI

Retain the HEMY dark rail, IBM Plex Sans, white category navigation, pale gray canvas and teal selection treatment, with Autodesk Content Catalog as the established reference. Main navigation has Library, Needs review, Categories and Sources. Counts describe definitions and review work. Source model is an optional filter, not the library's organizing identity. Search includes readable name, category, manufacturer/model, tags and curated specifications. Grid and list work across source files and show kind, important specifications and source availability; hide GUIDs from the main card.

Normal card click opens a definition inspector. Card arrow selects the same entry and opens a centered geometry/parameter dialog. Show curated values first, source suggestions/conflicts on request, and raw IFC under source details. Keep geometry errors local so definitions remain usable without an available model. Staff can edit definitions, approve/batch approve, archive/restore, review duplicate differences and merge, split variants, select geometry, and manage category aliases/templates. Sources retains upload/index/hide operations and adds Analyze and import drafts with progress. Existing source viewer is reusable inside Sources; the main landing page is always the approved library.

Use real empty states, native accessible dialogs, clear action outcomes, labeled controls, focus return and reduced-motion styling. Verify 1280px desktop and 390px mobile without horizontal overflow. Use functional affordances only; no FM action placeholders or fabricated content. Large review lists need search/category filters and batch selection, not one dialog per imported element.

## Evidence and acceptance

Real BS19/JV3 data contains repeated names with different categories and dimensions, sparse manufacturer/model values and instance-level reusable specifications. Preserve these differences rather than deleting duplicates based on names. Automated tests must cover unit conversion, explicit blank precedence, missing versus zero, conflicts, variant partitions, reviewed merge, repeat import, changed sources, revision races, persistence/restart, approved retention after hidden source and UI publication boundaries. Final Chrome verification imports real BS19/JV3 drafts, curates at least one real entry, confirms its geometry/properties in both inspector modes, verifies retention and mobile layout, and records actual counts and limits. Full suite, strict typecheck and production build must pass.
